# Списания «себе» в боте Chip & Dale — дизайн

**Дата:** 2026-08-21
**Статус:** согласовано, готово к плану реализации
**Автор:** Pavel + Claude

## Проблема

Когда команда берёт вино/алкоголь из магазина «себе», это нужно списать со склада
через **Stock Adjustment в Loyverse**. Сейчас это делается вручную и легко забывается —
бутылка ушла, а остаток в системе завышен, оборачиваемость и себестоимость врут.

Бот Chip & Dale уже умеет распознавать расходы и purchase orders. Добавляем третью
способность: **помнить незакрытые списания и напоминать о них**, пока человек не
сделает корректировку в Loyverse.

## Ключевое ограничение (определяет весь дизайн)

Публичный **Loyverse API не отдаёт историю Stock Adjustment'ов**. Доступны только текущий
остаток (`in_stock` по варианту) и чеки продаж. Отдельного эндпоинта «покажи корректировки»
нет. Значит, «пойти и проверить, списали по факту» напрямую невозможно.

**Решение:** источник истины — человек. Бот ведёт список незакрытых списаний и напоминает;
когда человек сделал Stock Adjustment в Loyverse, он жмёт кнопку «Списано» в боте или портале.
Бот **никогда не пишет в Loyverse** (API и не умеет корректировки, и по решению владельца
их делают руками).

## Принятые решения

| Развилка | Решение |
|----------|---------|
| Как проверять факт списания | Ручная кнопка «✅ Списано» (не авто-вывод по остатку) |
| Как заводить | Гибко: текст с триггером, фото+подпись с триггером, явное имя из Items |
| Причина/тип | Не спрашиваем — всё «себе», один тип |
| Где закрывать | Бот (`/writeoffs`) **и** раздел в портале mission-control |
| О чём напоминать в брифинге | Про **всё открытое**, с пометкой возраста |

## Поток данных

```
Пользователь (Telegram)
  │  «спиши просекко 2»  /  фото+«спиши 2»  /  явное имя Items
  ▼
Детектор триггера (спиши/списать/списание/взяли себе/себе)
  │
  ├─ текст  → Claude парсит {query, qty}
  └─ фото   → Claude vision читает этикетку → {name-догадка, qty из подписи}
  ▼
Фаззи-матч по каталогу Loyverse (/items + /inventory)
  ├─ 1 уверенный матч → карточка списания
  ├─ несколько        → инлайн-кнопки «какой из них?» → карточка
  └─ 0                → «не нашёл, напиши точнее»
  ▼
Карточка [✅ Записать] / [✖ Отмена]
  ▼ Записать
Supabase public.stock_writeoffs (status='pending')
  │
  ├─ Утренний брифинг → блок «Не списано: …» (всё открытое)
  ├─ Команда /writeoffs → список pending, у каждого «✅ Списано»
  └─ Портал /m/writeoffs → таблица + кнопка «Списано»
       ▼ Списано
     status='done', closed_at, closed_by  ← источник истины
```

## Компоненты

### 1. Детектор триггера и роутинг (в `01_agents/bot/src/index.ts`)

Триггерные слова (lowercase, в тексте или в подписи к фото):
`спиши`, `списать`, `списание`, `взяли себе`, `себе`, `списал`.

Роутинг сообщений расширяется так:
- **Фото + подпись**: если подпись содержит триггер → флоу списания; иначе (как сейчас) расход.
- **Текст**: если содержит триггер → флоу списания; иначе как сейчас (`looksLikeExpense` → расход,
  иначе `askClaude`). Триггеры списания не пересекаются с форматом расхода («856 интернет»).

Порядок проверки в `message:text`: pendingPhoto → **триггер списания** → looksLikeExpense → адресация боту.
В `message:photo`: подпись с триггером списания → списание; иначе существующая ветка (подпись=расход, без подписи=PO).

### 2. Разбор и матч (новый модуль `01_agents/bot/src/writeoff.ts`)

- `parseWriteoffText(text)` → `{ query, qty }` через Claude (модель `claude-sonnet-4-6`, как в `po.ts`).
  Кол-во по умолчанию 1, если не указано. `query` — очищенное название без триггерных слов.
- `parseWriteoffPhoto(base64, mime, caption)` → `{ query, qty }` через Claude vision:
  «прочитай бренд/название с этикетки, верни короткое имя для поиска; qty возьми из подписи».
- `matchCatalog(query)` → массив кандидатов `{ variant_id, item_name, in_stock }`:
  - тянем каталог как в `loyverse.ts::getStoreContext` (items + inventory, тот же 5-мин кэш можно переиспользовать);
  - локальный дешёвый фаззи-прескоринг (совпадение токенов/подстрок, без учёта регистра);
  - если топ-кандидат заметно оторван от второго → «уверенный матч» (один);
  - иначе вернуть топ-N (до 5) на выбор кнопками.

Матч только читает Loyverse; ничего не пишет.

### 3. Карточка списания (в `writeoff.ts`, по образцу `po-parse.ts`)

Состояние карточки НЕ хранится в памяти (переживает рестарт Railway): поля читаются обратно
из текста карточки, `variant_id` едет в callback-данных. Показывает: товар (имя из Loyverse),
кол-во, дата (Бангкок), кто. Кнопки:
- `✅ Записать` (`wo_confirm:<variant_id>`)
- `✖ Отмена` (`wo_cancel`)
- при мультивыборе — кнопки кандидатов (`wo_pick:<variant_id>`), затем показ карточки.

По «Записать» → `INSERT` строки со `status='pending'`.

### 4. Хранение — миграция `038_stock_writeoffs.sql`

```sql
create table if not exists public.stock_writeoffs (
  id          uuid primary key default gen_random_uuid(),
  variant_id  text,                 -- Loyverse variant_id (для будущих сверок)
  item_name   text not null,        -- как в каталоге Loyverse на момент записи
  qty         integer not null default 1,
  taken_date  date not null default (now() at time zone 'Asia/Bangkok')::date,
  taken_by    text,                 -- Telegram-имя, кто завёл
  status      text not null default 'pending',  -- 'pending' | 'done'
  closed_at   timestamptz,
  closed_by   text,                 -- кто нажал «Списано»
  created_at  timestamptz not null default now()
);
create index if not exists stock_writeoffs_status_idx on public.stock_writeoffs (status, taken_date);
```

Миграция применяется вручную в Supabase SQL Editor (как все прочие — см. `[[project_migrations_manual]]`).
Бот уже имеет `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` (тот же клиент, что `db.ts`).

DB-хелперы в `writeoff.ts`: `insertWriteoff(row)`, `listPending()`, `closeWriteoff(id, closedBy)`.

### 5. Напоминание в брифинге (в `01_agents/bot/src/briefing.ts`)

После основного текста добавляется блок (аналог `formatPaymentAlerts`):
если есть открытые списания — перечислить **все** `status='pending'`, отсортированные по
`taken_date` (старые сверху), с пометкой возраста в днях:

```
🍷 Не списано (3):
• 2× Prosecco Miravento — со вчера
• 1× Whispering Angel — 3 дня
• 1× Beluga — 5 дней
Закрой через /writeoffs, когда сделаешь Stock Adjustment в Loyverse.
```

Пустой список → блок не показывается.

### 6. Команда `/writeoffs` (в `index.ts`)

Выводит список pending, у каждого пункта — сообщение с кнопкой `✅ Списано` (`wo_close:<id>`).
Тап → `closeWriteoff(id, ctx.from)`, карточка редактируется в «✅ Списано: 2× Prosecco».
Пустой список → «Всё списано, чисто 👍».

### 7. Портал-раздел `/m/writeoffs`

- Реестр `lib/registry.ts`: новый item под **Operations** рядом с `purchase-orders`:
  `slug: 'writeoffs', name: 'Write-offs', icon: '🍷', route: m('writeoffs'), embed native`.
- Страница `app/(portal)/m/writeoffs/page.tsx`: таблица (товар, кол-во, дата, кто, статус, возраст),
  фильтр pending/all, кнопка «Списано» на pending-строке.
- API `app/api/m/writeoffs/route.ts`: `GET` (список, фильтр по статусу), `POST` (закрыть: id → done).
  Читает/пишет ту же таблицу `public.stock_writeoffs` через service-role клиент портала.

## Вне scope (YAGNI / возможные фазы 2+)

- Причины/категории списания (сейчас всё «себе»).
- Авто-вывод «списано по факту» из падения остатка (API не даёт историю; шумно).
- Запись Stock Adjustment прямо в Loyverse (API не умеет; делается руками).
- Редактирование кол-ва/товара в уже заведённой карточке (можно отменить и завести заново).

## Риски и заметки

- **Матч по каталогу — самое рискованное место.** Vision-догадка по этикетке и фаззи-скоринг
  могут промахнуться. Митигируем показом кандидатов и подтверждением человеком перед записью.
- **Разводка с расходом.** Фото+подпись сейчас = расход. Триггер списания в подписи перехватывает
  раньше — проверить, что обычные расходы не содержат слов-триггеров (не содержат).
- **Дубли.** Мягко: если тем же `variant_id` уже есть pending за сегодня — не блокируем, но можно
  показать хинт «уже есть незакрытое списание этого товара». (Опционально, не обязательно в MVP.)
